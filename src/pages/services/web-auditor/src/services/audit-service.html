Executive Summary

This report presents a comprehensive audit of the entire Volynx platform covering 45 Astro pages, 14 components, 4 layouts, 17 style files, 10 public scripts, and the Express backend. The audit identified 38 discrete findings organized by severity across 9 categories.

The frontend is well-structured with a strong Astro architecture, good visual design, and a solid centralized route system. However, the backend is fundamentally incomplete. The Express server only handles a single hardcoded Stripe price, with no endpoints for permission checking, usage logging, or token management. This means the entire monetization layer — plans, tokens, Pro gating — operates on client-side fallbacks only.

Authentication works but plan enforcement is scattered across 8+ files using raw string comparisons instead of the centralized helpers already defined in plans.ts. The i18n system has 44 missing keys and 85 orphaned keys. Several key pages (account, profile) show permanent placeholder data because their backend dependencies don’t exist yet.

Findings by Category

1. Backend & API (F-01 through F-05)

The Express backend (index.js) is the single largest blocker to a production-ready platform. It currently handles only one hardcoded Stripe price ID in subscription mode. The frontend expects three API endpoints that don’t exist:

  • /api/check-permission — expected by every tool page to verify plan and return usage limits
  • /api/log-usage — expected by all tools to record server-side usage for Pro billing
  • /api/create-checkout-session with lookup_key — expected by pricing page for dynamic plan/currency selection

The token system is defined in pricing.ts (Classes A–E, 1–20 tokens per action) and displayed on the pricing page, but no token balance, deduction, or redemption logic exists anywhere in the codebase. Token pack purchase buttons call a checkout endpoint that only supports subscriptions, not one-time purchases.

2. Authentication & Plan Logic (F-06 through F-15)

Authentication itself works — Supabase login, signup, token refresh, and session management are functional. The critical problem is how plan data is handled after authentication.

  • Scattered plan checks: The canAccess() and isPaid() helpers in plans.ts are never imported. Instead, raw comparisons like plan === 'pro' appear in 8+ files, creating a maintenance nightmare if plan names change.
  • Incomplete Pro gating: Only image-suite is in the proOnlyTools array in vx-auth-gate.js. Free users can access Studio converter, image-scaler, and qr-gen via /volynx-lab/studio/ paths.
  • Data model mismatch: Profile pages read profile?.plan from Supabase, but the actual plan comes from /api/check-permission — which doesn’t exist yet.
  • FreeUsageCounter broken: Reads volynx_plan from localStorage, but nothing ever writes that key. Always defaults to ‘free’.
  • No plan caching: Every Studio page load makes an API call with a 3.5s timeout and no cached fallback.
  • Race condition: image-suite calls detectPro() without await, then immediately renders UI before the plan check completes.
  • No cleanup on logout: Usage keys in localStorage persist across different user sessions on the same device.

3. Internationalization (F-16, F-17, F-33, F-36)

The i18n engine works correctly, but coverage has significant gaps:

  • 44 keys missing: Used in HTML via data-i18n but not defined in translations.js. The manifesto page alone has 24 missing keys. Cookie banner has 12 missing keys. Signup form is missing fullname and username keys.
  • 85 keys orphaned: Defined in translations.js but never referenced in any page. Entire sections for home, products, lab, login, devhub, and maintenance are unused.
  • Naming inconsistency: Manifesto uses flat keys (heroLabel, titleLine1) while every other page uses hierarchical keys (page.subkey).
  • Unused engine feature: data-i18n-aria is implemented in the i18n engine but never used in any page.

4. Links, Routes & CTAs (F-21, F-22, F-27, F-37, F-38)

The route system in routes.ts is well-designed, but not consistently used:

  • 22+ hardcoded paths: Product pages, dev-hub, dev-journey, and landing-express all have links written as raw strings instead of importing from ROUTES.
  • 10 dead buttons: The Icons Store page has 10 href="#" links (Collections, Favorites, View Pricing, View All) with no JavaScript handlers attached.
  • Duplicate page: volynx-icons-store exists under both /products/ (30KB full page) and /dev-hub/ (316B minimal). The route points to dev-hub; the products version is orphaned.
  • Dead project link: Portfolio Pro Kit has a “View Project →” link pointing to # with no handler.

5. Content & Page Quality (F-19, F-20, F-28, F-29, F-30)

  • Account page: All dashboard stats (token reserve, presets, brands, projects) permanently show “—” because no backend populates them.
  • Profile page: Form fields for name, handle, email, location appear but have no visible submit handler or data loading logic.
  • Builder page: Marketing landing page only — no actual editor, canvas, or publishing interface. Should be clearly communicated as “coming soon.”
  • Status & Changelog: Both have minimal placeholder content (2 entries each) that doesn’t reflect an active platform.

6. Layout & Structure (F-18, F-24)

The project has 4 layout files (BaseLayout, HomeLayout, FlagshipLayout, LegalLayout), but 4 pages bypass them entirely:

  • services/index.astro — raw HTML with custom header/footer
  • dev-journey/index.astro — raw HTML with 600+ lines of inline CSS
  • manifesto/index.astro — raw HTML with extensive inline styles
  • profile.astro — raw HTML without Astro layout structure

Headers and footers are also inconsistent: 3 different header components (FlagshipHeader, VxHeader, custom) and 3 footer components are used across pages with no clear pattern for which pages get which.

7. Pricing Consistency (F-23)

Studio Pro pricing is hardcoded as £19/month directly in the Studio index page HTML. If pricing.ts is updated, this value won’t follow. All prices should be sourced from the centralized pricing data file.

8. SEO & Forms (F-09, F-31, F-32)

  • Contact form: Still has a TODO comment and points to formspree.io/f/FORM_ID. Sales leads from the contact form are being lost.
  • Services form: Uses mailto: action, which is unreliable and doesn’t provide proper data capture.
  • Missing OG tags: 6 pages lack Open Graph metadata: contact, profile, changelog, tools, status, manifesto.

9. Code Quality (F-34, F-35, F-36)

  • Dead code: plans.ts defines canAccess() and isPaid() but they’re never imported anywhere.
  • Fragile pattern: window.__vxTool is set manually in each tool page with no validation.
  • Unused engine feature: data-i18n-aria is implemented but never used.

Recommended Action Plan

• Phase 1 — Backend Foundation (Critical)

Without these, the platform cannot monetize or enforce plans. This is the single most important workstream.

  1. Build /api/check-permission endpoint — returns plan, limits, usage, and useLocalStorage fallback flag
  2. Build /api/log-usage endpoint — records tool usage per user with timestamps
  3. Upgrade /api/create-checkout-session to accept lookup_key parameter and support both subscription and one-time purchase modes
  4. Implement token balance tracking, deduction on tool use, and purchase redemption
  5. Configure Formspree (or equivalent) for the contact form — replace FORM_ID placeholder

• Phase 2 — Plan Logic Centralization (High)

Eliminates scattered raw string comparisons and fixes Pro gating holes.

  1. Refactor all plan checks to import and use canAccess() / isPaid() from plans.ts
  2. Add all Studio tools to proOnlyTools array (converter, image-scaler, qr-gen)
  3. Fix FreeUsageCounter to write/read volynx_plan correctly, or source plan from API response cache
  4. Fix detectPro() race condition in image-suite (await before rendering UI)
  5. Add plan caching with TTL to reduce redundant API calls
  6. Clear usage localStorage keys on logout

• Phase 3 — i18n & Links Cleanup (High)

  1. Add the 44 missing translation keys to translations.js (manifesto, cookie banner, signup)
  2. Remove or reconnect the 85 orphaned translation keys
  3. Replace all 22+ hardcoded paths with ROUTES imports
  4. Fix 10 dead href="#" buttons on Icons Store page
  5. Delete orphaned /products/volynx-icons-store/ duplicate

• Phase 4 — Layout & Content Polish (Medium)

  1. Migrate services, dev-journey, manifesto, and profile to use proper Astro layouts
  2. Standardize header/footer component usage across all pages
  3. Wire account and profile pages to real backend data (or show honest “coming soon” states)
  4. Source Studio Pro price from pricing.ts instead of hardcoding in HTML
  5. Add Open Graph tags to the 6 pages missing them
  6. Populate status page and changelog with real content
  7. Replace services page mailto: form with proper form handling
This audit was performed by analyzing every file in the Volynx repository: 45 Astro pages, 14 components, 4 layouts, 17 style files, 10 public scripts, and the Express backend. Each finding was verified against actual source code, not assumptions.
